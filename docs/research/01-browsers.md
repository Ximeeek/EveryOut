# Browser session data on Windows 10/11

Research dossier for EveryOut, Phase 5. Evidence cutoff and access date: 2026-09-30.
Scope: browser-local session persistence; no implementation or architecture decision.
Excluded: saved passwords, autofill, history, passkeys, operating-system account state,
non-browser applications, developer tools, and multi-account mode.

Evidence convention: each factual paragraph or table row ends with a verification tag.
A tag verifies only the adjacent claim, not a proposed deletion policy. `[HYPOTHESIS]`
marks an inference, unresolved behavior, candidate path, or proposed verification criterion.
Source-code evidence describes the retrieved upstream implementation; it does not prove
that every vendor's current stable build enables that implementation.

### Preservation boundary

Exclude password stores (`Login Data` and account variants), autofill-bearing
`Web Data`/account variants, history stores (`History`, `Archived History`,
`Visited Links`, `Top Sites`, `Shortcuts`) and all passkey material.
These filenames are preservation candidates, not a verified cross-vendor schema map. [HYPOTHESIS]

Browser documentation distinguishes cookies/site storage from passwords, passkeys,
autofill and history. A whole-profile reset would exceed the requested session scope.
[VERIFIED: https://support.google.com/chrome/answer/2392709?co=GENIE.Platform%3DDesktop&hl=en, accessed 2026-09-30] [HYPOTHESIS]

For mixed stores, report the preservation conflict rather than treating the whole file as
deletable. Removing encryption keys from Local State could make excluded data inaccessible;
deleting Preferences could destroy unrelated settings or Wallet state. [HYPOTHESIS]

## 2. App-Bound Encryption and live-browser constraints

Chrome introduced App-Bound Encryption on Windows in version 127, initially for cookies.
Its privileged service validates the requesting application's identity; another ordinary
application is not authorized to decrypt the protected data. This is a protection boundary,
not an absolute guarantee against elevated malware or injection. [VERIFIED: https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html, accessed 2026-09-30]

The upstream provider defines ciphertext tag `v20`, key header `APPB` and preference
`os_crypt.app_bound_encrypted_key` in Local State. Eligibility and deployment conditions
mean that neither every profile nor every Chromium derivative can be assumed to use v20.
[VERIFIED: https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/os_crypt/app_bound_encryption_provider_win.h, accessed 2026-09-30] [VERIFIED: https://raw.githubusercontent.com/chromium/chromium/main/chrome/browser/os_crypt/app_bound_encryption_provider_win.cc, accessed 2026-09-30] [HYPOTHESIS]

Deleting a file is governed by Windows deletion permissions and handle-sharing rules:
DeleteFile can fail for files opened without deletion sharing. The API does not require
application-level decryption. [VERIFIED: https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew, accessed 2026-09-30]

Inference: deleting an eligible, closed cookie database need not decrypt cookies.
SQLite locking, open handles, in-memory session state and browser writes are practical
obstacles; “SQLite locks are the only problem” is too strong, since permissions, background
processes and incomplete artifact coverage can also defeat a wipe. [HYPOTHESIS]

From Chrome 136, the `--remote-debugging-port` and `--remote-debugging-pipe` switches
are ignored for the default data directory; a non-default `--user-data-dir` is required.
Chrome for Testing retains the previous behavior. [VERIFIED: https://developer.chrome.com/blog/remote-debugging-port, accessed 2026-09-30]

The broader claim “CDP is unusable on the default profile after 136” is not established.
Chrome subsequently documented a consent-based running-browser debugging flow for
Chrome 144+, enabled through `chrome://inspect/#remote-debugging`.
This does not establish an unattended, secret-free EveryOut clearing interface.
[VERIFIED: https://developer.chrome.com/blog/chrome-devtools-mcp-debug-your-browser-session, accessed 2026-09-30] [HYPOTHESIS]

## 4. Device Bound Session Credentials

Google announced public availability on Windows in Chrome 146 on April 9, 2026.
DBSC uses hardware-backed keys, such as a Windows TPM, to bind a session to the device;
refreshing short-lived cookies requires proof of key possession. Websites must implement
registration and refresh endpoints. It does not automatically protect every website.
[VERIFIED: https://blog.google/security/protecting-cookies-with-device-bound-session-credentials/, accessed 2026-09-30]

The draft specification requires clearing sessions and keys with site data and extends
Clear-Site-Data handling. It distinguishes these session keys from long-lived WebAuthn
credentials. DBSC session material must not be confused with excluded passkeys.
[VERIFIED: https://w3c.github.io/webappsec-dbsc/, accessed 2026-09-30]

Chrome's network context names `Device Bound Sessions`; upstream SessionStore persists
session records and wrapped keys and has its own session deletion operation.
[VERIFIED: https://chromium.googlesource.com/chromium/src/+/HEAD/chrome/browser/net/profile_network_context_service.cc, accessed 2026-09-30] [VERIFIED: https://raw.githubusercontent.com/chromium/chromium/main/net/device_bound_sessions/session_store_impl.cc, accessed 2026-09-30]

Wipe implication: removing only Cookies while retaining DBSC metadata/key access may allow
cookie refresh. Consider the complete session store and associated browser-managed key
references; the exact minimal offline set, including earlier Google bound-session
implementations, is unresolved. Do not propose deleting TPM-wide key material. [HYPOTHESIS]

Verification implication: immediate absence of Cookies is insufficient. Later controlled
validation should cover browser restart, cookie expiry and attempted refresh on an adopted
test site, plus a non-adopted control. File metadata can show targeted persistence gone,
but cannot prove server logout, TPM-key destruction or absence of automatic new login.
These are future research criteria, not experiments performed in this phase. [HYPOTHESIS]

## 6. Extensions and risky retained state

Chrome exposes persistent local/sync storage and memory-only session storage; clearing
browsing data does not generally clear extension storage. Mozilla warns that extension
storage is not encrypted and should not hold confidential information. Those APIs can
nevertheless hold application-defined state, independently of website cookies.
[VERIFIED: https://developer.chrome.com/docs/extensions/reference/api/storage, accessed 2026-09-30] [VERIFIED: https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage, accessed 2026-09-30]

Candidate risk labels for later catalog review, without inspecting stored values: [HYPOTHESIS]

| Proposed label             | Evidence required before assignment                                                                         | Consequence to disclose                                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Authentication persistence | Public extension source/docs showing tokens, device registration, session or persistent “remember me” state | Retaining data may preserve access; deleting can force full re-login. [HYPOTHESIS]                               |
| Vault cache                | Public source/docs showing offline vault data or persisted unlock/session material                          | Removing a cache can lose unsynced local data; process exit and disk wiping have different effects. [HYPOTHESIS] |
| Wallet/key material        | Public source/docs showing encrypted vault, seed/private-key persistence, or local-only recovery dependency | Removing encrypted state can irreversibly remove access even if it was locked. [HYPOTHESIS]                      |
| Unknown/shared storage     | Unreviewed extension or state mixed into origin/partition stores                                            | No guarantee of safe per-extension exclusion or complete logout. [HYPOTHESIS]                                    |

Brave explicitly warns that deleting all browser data also deletes Rewards/Crypto Wallet
data and may lose funds/access. A locked encrypted wallet is still preservation-sensitive;
“encrypted” does not make deletion safe. [VERIFIED: https://support.brave.com/hc/en-us/articles/4413256282765-How-do-I-delete-my-data-in-Brave, accessed 2026-09-30] [HYPOTHESIS]

AutoLogout documents “Preserve Dashlane extension”: cleanup skips selected **shared
Chromium storage paths**, trading session-cleanup coverage for extension continuity.
This verifies a real compatibility mode, not correctness or isolation of its deletion
implementation. [VERIFIED: https://github.com/TagSteel/AutoLogout, accessed 2026-09-30]

Installed-extension ID/directory presence can support a known-risk catalog lookup without
reading payloads; it cannot establish an extension's unlocked state. Reading a manifest
for identity/permissions would be another explicit metadata-read exception, and permissions
alone cannot prove vault semantics. [HYPOTHESIS]

## Open questions

- What exact release/channel/profile fixtures establish a complete inventory for all six
  products, including relocated profiles, vendor partitions and migration leftovers?
  Upstream HEAD/main is not a stable-release contract. [HYPOTHESIS]
- How closely do shipping Chrome token stores match the verified upstream Web Data layout,
  and what migration variants exist? What is the corresponding Edge Microsoft/Entra and
  Opera/Vivaldi identity inventory? [HYPOTHESIS]
- Which Chrome Windows builds and other vendors actually enable cookie synchronization,
  DOM-storage SQLite migration, encrypted session files and DBSC? Source constants alone
  do not establish shipping behavior. [HYPOTHESIS]
- Does retaining browser identity recreate site login after closed-browser deletion, and
  what is the minimal offline set that prevents it without touching excluded data?
  Confirm Google, Microsoft/Entra and Mozilla/Opera/Vivaldi service behavior separately.
  [HYPOTHESIS]
- Can Firefox account secure-store remnants be invalidated without reading secrets or
  deleting saved-password/key stores, particularly with a locked Primary Password?
  [HYPOTHESIS]
- What DBSC metadata and browser-owned key references must disappear to prevent refresh,
  and how does earlier Google bound-session persistence interact with the standard?
  Local deletion must not be claimed as remote revocation or TPM-wide erasure. [HYPOTHESIS]
- Which extension IDs/versions carry vault or Wallet recovery risk, and can any exclusion
  be scoped without preserving unrelated website sessions in shared stores? [HYPOTHESIS]
- Which non-secret configuration and registry fields, if any, should receive explicit
  read exceptions? What privacy minimization and false-positive rules would apply?
  [HYPOTHESIS]
- Which metadata signals can only say “unknown”, and what future authorized process/handle
  checks and isolated test-site validation would be necessary for stronger claims?
  [HYPOTHESIS]
